# R2 review — E6 throughput and bursts

1. **blocker — `apps/eval/src/harnext_eval/e6/run.py:245-249, 273-303`; `apps/eval/src/harnext_eval/e1/policies.py:315-347`; `apps/eval/tests/test_e6/test_runner.py:111-129`** — The spec requires the two-lane arm to use router R5. R5 determines anomaly eligibility with `raw >= threshold` and records the volume/confirmation decision, but the E6 wrapper throws that decision away: `candidate = score > -1e11` makes every ordinary finite HBOS score a deviation candidate. The causal budget therefore admits whichever eligible event happens to cross the next prefix quota, not R5 anomalies. The cited test injects `AlwaysCandidate`, so it cannot fail when the real R5 threshold is ignored. **Minimal fix:** expose and call a shared causal R5 decision API (including the threshold/eligibility result), then test real R5 with one above-threshold and one below-threshold event.

2. **blocker — `apps/eval/src/harnext_eval/e6/run.py:453-477, 595-650, 1280-1292`** — Exact `SLO_att` uses fast-lane `t_agent_start` for urgent events. The simulator labels the start of a batch fold as `agent_start` for every batch item and includes all urgent rows, including non-admitted batch rows, in `urgent_slo_attainment` and paired `two_slo`. With compressed smoke windows, an urgent event can therefore satisfy the 2 s fast-lane SLO without ever entering the fast lane. The observed smoke output has `deviation_admissions = 0` yet `urgent_slo_attainment = 1.0` and every gap is zero (`apps/eval/out/20260830T212140Z-baseline-minimal/e6/seed-1/gap_by_b.csv:2-17`). **Minimal fix:** treat a two-lane urgent event without a fast-lane agent start as a miss/infinite latency; keep batch fold start/commit as separate batch measurements, and add a test where an urgent batch event fails the fast SLO.

3. **blocker — `apps/eval/src/harnext_eval/e6/run.py:862-878, 1599-1628`; `apps/eval/tests/test_e6/test_runner.py:291-332`** — The real-profile Kafka path is not runnable through the declared matrix. `external_records_to_run` returns the default empty `route_decisions` frame, but guard evaluation unconditionally selects its `event_id` and `lane` columns, so a research run reaches a `KeyError` at the first guard cell. The fixture test calls only the adapter and never runs `run_benchmark` with Kafka, so R1 fix claims 1, 15, and 28 are not genuine end to end. **Minimal fix:** require/parse per-event route-decision telemetry for Kafka cells (including guard features), make guard comparison consume it, and add a fixture-backed Kafka `run_benchmark` test through all output stages.

4. **blocker — `apps/eval/src/harnext_eval/e6/run.py:1738-1778`; `apps/eval/tests/test_e6/test_runner.py:335-379`** — The validity list is not a gate. `run_benchmark` records check values but returns and publishes the primary result regardless of failures; the bounded benchmark test checks files and matrix dimensions but never asserts the checks. The R2-required `make eval-smoke` run exited successfully while `generator_p99_skew_le_1ms`, `repetitions_p99_within_20pct`, and `service_time_constant` were all false (`apps/eval/out/20260830T212140Z-baseline-minimal/e6/seed-1/results.json:245-253`; rendered as FAIL in `report.html:93-95`). These are applicable E6 validity failures, not declared smoke N/A conditions. **Minimal fix:** mark the E6 result invalid and suppress/clearly invalidate the primary whenever an applicable check fails (or abort the run), make smoke use a deterministic clock/harness that can pass, and add an end-to-end assertion that every applicable smoke check passes.

5. **blocker — `apps/eval/src/harnext_eval/e6/run.py:293-305, 673-684, 1749-1751`; `apps/eval/tests/test_e6/test_runner.py:111-129`** — The fast-lane budget is not enforced over all admissions. Rule admissions are unconditional and excluded from both the prefix allowance and `budget_compliant`; only deviation admissions are compared with `floor(rule_negative_seen * budget_pct)`. Thus total fast admissions can exceed the frozen percentage while the reported check is true (the smoke guard cell has 1 rule admission among 23 events at a 2% budget but reports compliance). The test policy always returns no rule, so it cannot detect this. **Minimal fix:** define the pre-registered treatment of the rules floor within the total admission budget, enforce that total causally (or explicitly report rule-floor overrun as invalid), and test a rule-heavy prefix.

6. **major — `apps/eval/src/harnext_eval/e6/run.py:384-389, 453-459, 558-565`** — The single-lane baseline is folded into per-entity batch windows: lane `single` is classified as batch, buffered, and serviced once per fold. That changes both the service unit and offered work relative to a two-lane design whose fast events are serviced per event, so the comparison does not isolate lane design and the “single-lane knee” is a knee of an amortising folder. **Minimal fix:** specify and implement the single shared agent queue baseline with the same per-event fake service, or otherwise use an explicitly pre-registered equivalent amount of work in both designs; test the number of service invocations per input event in both arms.

7. **major — `apps/eval/src/harnext_eval/e6/run.py:277-303, 1241-1260, 1595-1638`; `apps/eval/tests/test_e6/test_runner.py:132-193`** — R1 fix 4 is only partial. Guards use only the first baseline key even though R5 scores the maximum across keys; “multi-window” accepts any historical earlier candidate window because `_anomaly_windows` is never expired, rather than confirmation in the required distinct preceding window. More importantly, the actual benchmark does not require an ablation to change any decision: the smoke run wrote `changed_events_vs_full = 0` for all three removals (`results.json:3625,3673,3721,3769`). The unit test proves hand-built `AlwaysCandidate` examples can differ, not that the registered anomalous cell is non-vacuous. **Minimal fix:** carry the winning R5 baseline key/eligibility into guard state, require the intended adjacent-window confirmation, and invalidate any guard cell whose named removal changes no routed event on the registered fixture.

8. **major — `apps/eval/src/harnext_eval/e6/run.py:745-857`** — The Kafka summariser does not implement the literal exact scores. Unlike the in-process path, it never receives or applies the declared burst boundaries, computes fast and urgent histograms over the whole schedule, hard-codes `p99_trend_s_per_bucket` and partition-lag Gini to zero, and emits neither drain nor recovery time. Consequently Kafka knee stability, burst percentiles, skew, drain, recovery, and demand inputs can look valid without being measured. **Minimal fix:** pass schedule-plan boundaries into the adapter, retain timestamped per-partition lag samples, compute every exact metric with the shared functions, and reject missing required telemetry instead of substituting zero.

9. **major — `apps/eval/src/harnext_eval/e6/run.py:753-803, 958-980`; `apps/eval/tests/test_e6/test_runner.py:291-332`** — Kafka duplicate/miss/DLQ accounting is not the required per-lane accounting. “Expected by lane” is built from observed outputs, so an event with no output can only be assigned to synthetic lane `unknown`, never its actual fast/batch lane. Consumption stops immediately after all unique IDs have appeared, so later duplicate deliveries are missed, and `dlq` is merely summed from successful output records rather than read from a DLQ. The fixture explicitly accepts `missed_unknown`, masking the defect. **Minimal fix:** obtain expected route decisions before completion, consume through a declared quiescence/timeout interval, read the DLQ topic, and report expected/unique/duplicate/missed counts per real lane.

10. **major — `apps/eval/src/harnext_eval/e6/run.py:531-537, 943-945`; `apps/eval/tests/test_e6/test_loadgen.py:70-92`** — The worker-kill condition is not supported faithfully. The simulator only delays the last worker in the batch pool (so it may not affect the fast lane or even a busy partition), while Kafka silently skips the control marker and sends no kill/restart command at all. The test asserts only that a marker is timestamped at the peak, not that a worker goes down, restarts, creates lag, and recovers. **Minimal fix:** add a deployment control/telemetry seam for an actual worker outage, select and log the affected worker/partitions, and test a nonzero outage followed by recovery to measured pre-kill lag.

11. **major — `apps/eval/src/harnext_eval/e6/run.py:1373-1396, 1468-1543, 1595-1615`; `apps/eval/tests/test_e6/test_runner.py:335-365`** — R1 fix 7's “complete research cross-product” is not present. Bursts cover all topologies, but the steady sweep/knee is always only 8 partitions × 1 worker, and guard ablations use only the first topology and one selected plan/repetition. The test deliberately supplies only two topologies and checks the burst table; it does not exercise the research profile or guard/topology cross-product. **Minimal fix:** either run and report knee and guard factors for every pre-registered topology/repetition or pre-register a clearly non-factorial reference topology; add an exact research-matrix construction test that does not require live brokers.

12. **major — `apps/eval/src/harnext_eval/e6/run.py:1019-1055, 1367-1371`** — Research calibration does not calibrate the selected pipeline. `run_benchmark` always invokes the fixed in-process `calibration_run`; the research Kafka transport, separate generator clock, broker, and deployed fake harness are bypassed. A passing calibration therefore says nothing about coordinated omission or latency in the real path. **Minimal fix:** parameterise calibration with the selected `RunnerConfig` and run the 10 ms pass-through through Kafka in research mode, requiring both median and p99-flatness before benchmark cells run.

13. **major — `apps/eval/src/harnext_eval/e6/loadgen.py:730-754, 787-802`; `apps/eval/src/harnext_eval/e6/run.py:1179, 1233-1238, 1752-1754`** — Workload-B validity is misstated. Research sweeps hard-coded B targets `{0.25, 0.5, 0.75}` but never includes the fitted Corpus-R B required by procedure step 1; Poisson is labelled `target_b = 0` without any convergence/tolerance check even when realised B is far away. In the mandated smoke run, Poisson rows were labelled B=0 while realised B was about -0.93. The Poisson validity predicate also allows a large Poisson advantage whenever the anomalous advantage is similarly large (`abs(poisson_gap) <= abs(primary_gap)+0.05`), which does not require shrinkage toward zero and passes the completely vacuous 0-vs-0 result. **Minimal fix:** include the fitted B target, enforce and report a tolerance for every B-labelled control, and pre-register a direct near-zero Poisson-gap bound plus a non-vacuous anomalous contrast requirement.

14. **major — `apps/eval/src/harnext_eval/e6/loadgen.py:715-719, 788-803`; `apps/eval/src/harnext_eval/e6/run.py:370-376, 526-528, 1273-1278`** — Burst-window offsets are measured from the earliest generated entry, not from the schedule's declared start. `SchedulePlan` does not retain `begin`; both the runner and paired scorer subtract the first entry. Poisson/Pareto schedules need not start at offset zero, so at realistic low rates this shifts the 10-minute burst window and can include/exclude the wrong urgent events and lag samples. **Minimal fix:** store the schedule origin in `SchedulePlan`, pass it to both transports/scorers, and test a schedule whose first event occurs well after the origin.

15. **major — `apps/eval/src/harnext_eval/e6/run.py:821-856, 971-977`** — Broker monitoring is presence-only and unscoped. Every cell rereads the whole telemetry file, takes global maxima/sums without timestamp or run/cell filtering, and passes `broker_telemetry_present` if any CPU and disk keys exist. Stale samples from another run can therefore satisfy the validity check and every cell receives identical resource values. **Minimal fix:** require timestamped, run-ID-tagged telemetry, slice it to each cell's interval, validate coverage, and report saturation/trend diagnostics per cell.

16. **major — `apps/eval/src/harnext_eval/e6/loadgen.py:657-659`; `apps/eval/src/harnext_eval/e6/run.py:900-970`** — Kafka paired runs are vulnerable to cross-cell contamination. Injected urgent IDs depend only on situation and pulse, so the same IDs recur in every shape, load, topology, repetition, and lane arm; output consumers have no run/cell ID filter and accept any expected ID arriving after they start. A delayed output from the preceding arm can therefore be scored in the next arm, breaking paired comparisons nondeterministically. **Minimal fix:** keep a stable logical situation ID but make event IDs unique per frozen schedule/cell, attach a run/cell ID to input and echoed output, and filter the consumer on both before scoring.

17. **major — `apps/eval/tests/test_e6/test_runner.py:86-108, 111-129, 291-379`; `apps/eval/tests/test_e6/test_loadgen.py:70-92`** — The tests still do not test several claims they name. The steady test accepts either knee; the budget test replaces R5 and has no rules; the Kafka test bypasses the Kafka runner and expects unknown-lane misses; the bounded benchmark does not assert validity, a nonzero anomaly gap, a near-zero Poisson gap conditional on a real anomaly effect, or non-vacuous guards; and the kill test checks only marker placement. All 29 E6 tests pass while the full smoke report has three failed E6 checks and identical arm scores. **Minimal fix:** add mutation-sensitive claim tests for real R5 thresholding, total budget, exact single-vs-two lane SLO semantics, research adapter completion, worker recovery, all validity gates, and non-vacuous registered contrasts.

**R1 verification summary.** By reading both implementation and covering tests, fixes 2, 5, 6, 8, 9, 11, 12, 14, 20, 21, 23, 24, and 26 are materially present for the in-process path. Fixes 1, 3, 4, 7, 10, 13, 15-19, 22, 25, 27, and 28 are incomplete or not genuinely covered for the reasons above. In particular, the research factory exists as configuration, but its Kafka benchmark cannot finish and does not compute the same exact scores, so this is not merely a supported-not-run execution-profile concern.

**Verdict — FAIL.** E6 is still not faithful enough to trust: the smoke profile publishes results despite three applicable validity failures, routes no urgent deviations, gives batch-folded urgent events credit for the fast-agent SLO, and produces identical lane and guard-arm scores. The configured research path is also not trustworthy or runnable through completion: it does not apply real R5 eligibility, excludes rule admissions from the budget, crashes at guard decision comparison, ignores worker-kill control, and substitutes missing exact Kafka metrics. Before results can be trusted, E6 must enforce the actual total-budgeted R5 decision, score only real fast-agent starts, make all applicable validity checks gating, make smoke contrasts non-vacuous and deterministic, and complete/test the Kafka path with burst-scoped metrics, route/DLQ/duplicate telemetry, worker control, cell isolation, and the declared matrix.

## Round 3 fixes

- Finding 1 → the two-lane arm now owns a real `GuardedHBOSPolicy` R5 object with its configured absolute-volume and adjacent-window guards active; routing consumes R5's actual `score >= threshold`, winning baseline key, and eligibility record instead of treating every finite score as anomalous → `test_two_lane_uses_real_r5_threshold_and_its_guard_object` covers one below-threshold and one above-threshold decision and asserts the registered guard settings.
- Finding 2 → batch observations retain their own service-start timestamp but have no qualifying fast-agent latency, so urgent batch events are infinite-latency SLO misses; exact in-process/Kafka, paired, self-amplification, and fairness scoring now count only fast-lane urgent starts (single-lane starts remain the paired baseline) → `test_urgent_batch_event_is_a_fast_slo_miss` proves an urgent event that stays in batch cannot attain the 2 s fast SLO, and `test_fixture_backed_kafka_schema_counts_unique_ids_and_telemetry` asserts the same external-record denominator semantics.
- Finding 4 → every finite/applicable `checks.*` value now gates the published E6 primary through `primary.valid` and `primary.invalid_reasons`, with a matching structured validity check; invalid headline `burst_slo.png` charts receive an explicit red `INVALID PRIMARY` banner. Smoke uses deterministic intended/send and service clocks so skew, constant-service, and repetition checks are stable → `test_bounded_benchmark_has_paired_matrix_and_exact_outputs` asserts every applicable smoke check passes, while `test_invalid_validity_check_gates_primary_and_annotates_headline_chart` forces a failure and verifies both primary invalidation and chart annotation.
- Finding 5 → the causal allowance is now `floor(all_events_seen * budget_pct)` and gates rule plus deviation admissions; a rule consumes capacity before deviation eligibility is considered, over-budget rules remain batch events, and `rule_admission_overflow`, total admissions, and total routed events are reported. `budget_compliant` now checks total admissions → `test_rule_admissions_are_gated_by_total_prefix_budget_and_overflow_recorded` exercises a rule-heavy stream and every prefix.
- Finding 6 → the single-lane baseline now uses one shared FIFO queue, enqueues every input immediately without entity windows, and invokes the same configured fake service once per event; observations log service order and invocation count → `test_single_lane_is_fifo_per_event_with_same_fast_service_model` compares single and all-fast two-lane invocations, FIFO order, window absence, and service time.
