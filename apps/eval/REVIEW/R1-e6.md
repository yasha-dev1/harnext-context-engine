# R1 review — E6 throughput and bursts

1. **blocker — `apps/eval/src/harnext_eval/e6/run.py:839-869, 1109-1116`** — The spec requires a systems benchmark with open-loop load from a separate host, the full fitted-rate/10-minute-burst procedure, and the real pipeline using a deterministic fake harness. The registered experiment always calls `run_benchmark` with the default `BenchmarkConfig` (0.16 s steady runs and 0.12 s bursts) and default in-process transport; `BenchmarkConfig.research()` is never selected, including for a non-smoke CLI run. The Kafka transport cannot be selected through `BenchmarkConfig` or `E6Experiment`. **Minimal fix:** make research mode the normal registered run, make smoke mode explicit, and pass a deployment/transport configuration that runs the full matrix against Kafka from the separate load-generator host.

2. **blocker — `apps/eval/src/harnext_eval/e6/loadgen.py:232-263`; `apps/eval/src/harnext_eval/e6/run.py:178-200`** — The primary gold must be independently injected urgent events, while router features must contain only information available at event time and must not contain the answer. The generator writes the gold boolean as `e6_urgent` into each event, and the router reads both that field and `ScheduleEntry.urgent`, assigns score 1, and admits it directly. This is target leakage/oracle routing, so the primary two-lane result cannot measure R5. **Minimal fix:** keep urgency/situation gold in a sidecar keyed by event ID, never in the event or router input, and route solely from causal R5 features.

3. **blocker — `apps/eval/src/harnext_eval/e6/run.py:142-230`; `apps/eval/configs/e6-twolane.yaml:3-7`** — The two-lane condition is explicitly “router R5,” including per-entity HBOS, rules, guards, and a budget. `E6RouterPolicy` is a separate hard-coded score (`1.0` for gold urgency, otherwise `0.2`), never fits or invokes R5/HBOS, ignores `router.deviation.enabled`, and never reads or enforces `budget_pct`; the supplied two-lane config even disables deviation and all guards. Admissions can therefore greatly exceed the configured 2% budget. **Minimal fix:** use the actual causal R5 policy and streaming budget mechanism, configure deviation/full guards on the two-lane arm, and log/assert admitted share against the frozen budget.

4. **major — `apps/eval/src/harnext_eval/e6/run.py:195-229, 967-991`** — The guard ablations must remove the absolute-volume floor, multi-window confirmation, and situation dedup one at a time from a faithful full guard. Here the “absolute floor” is a threshold on the fabricated anomaly score, not absolute volume; removing it is vacuous because base admission still uses `score >= max(absolute_floor, 0.5)`. The multi-window guard rejects after five recent admissions rather than requiring confirmation across windows. Rules are incorrectly subjected to the absolute floor, and dedup falls back to `entity:type`, which conflates unrelated situations. **Minimal fix:** implement the real R5 volume and confirmation semantics, keep the rules floor unconditional, deduplicate by constructed situation ID, and add an assertion that each ablation changes only its named guard and is non-vacuous on the fixture.

5. **major — `apps/eval/src/harnext_eval/e6/loadgen.py:217-218, 253-255`; `apps/eval/src/harnext_eval/e6/run.py:885-905`** — Section 2/8 requires every comparison to be paired on the identical frozen stream. Each matrix cell regenerates a schedule with `datetime.now()`, and the absolute timestamp is included in event IDs, so lane arms do not share timestamps or IDs. Different topologies also deliberately use different seeds (`seed + partitions + workers`). **Minimal fix:** pre-generate and persist one schedule per workload/load/repetition with a fixed start and IDs, then replay that exact schedule unchanged through every lane, topology, and guard arm.

6. **blocker — `apps/eval/src/harnext_eval/e6/run.py:296-306, 372-385, 400-443`** — The topology factor is partitions `{8,32}` × workers `{1,4}` in a real pipeline. The fake path has one global priority queue consumed by all workers; partitions only label counters and never constrain assignment or parallelism, while both lanes share the same queue. Thus changing partitions cannot change capacity, and the benchmark is not testing the named topology or actual lane isolation. **Minimal fix:** run the actual partitioned Kafka consumer groups and lane queues, or make the faithful simulator enforce partition ownership, per-partition ordering, and separate lane resources before using its results.

7. **major — `apps/eval/src/harnext_eval/e6/run.py:753-803, 857-870, 881-947`** — The condition table is factorial over lane design, load, shape, and topology, and the validity check requires repeated p99s. The steady `{0.25,0.5,1,2,4}×` sweep runs only single-lane at the default 8-partition/1-worker topology. Burst cells run only once; `repetitions` is used solely for steady runs. Entity cardinality is fixed even though `demand(l)` must be measured at each load and cardinality. **Minimal fix:** execute the declared cross-product (or document a pre-registered non-factorial design), repeat every measured burst cell at least three times, and add the cardinality sweep needed for demand.

8. **major — `apps/eval/src/harnext_eval/e6/loadgen.py:267-307, 332-357`; `apps/eval/src/harnext_eval/e6/metrics.py:17-33`; `apps/eval/src/harnext_eval/e6/run.py:1032-1052`** — The Poisson control must show the two-lane advantage shrinking toward zero for the same identifiable urgent population. Non-anomalous schedules, including Poisson, create no urgent events. Empty-set SLO attainment is returned as 0 for both arms, so `poisson_gap == 0` and the validity check passes trivially. The same makes urgent SLO scores for steady, benign-flash, Pareto, Zipf-hot, and worker-kill cells vacuous. **Minimal fix:** inject the same independent urgent situations into every control shape, treat an empty urgent denominator as invalid/NA, and fail rather than pass the control when no urgent gold exists.

9. **major — `apps/eval/src/harnext_eval/e6/run.py:896-906, 1020-1038`** — The exact primary requires `gap(B) = SLO_att_two - SLO_att_single` as a function of burstiness B. The code evaluates a single anomalous workload, at only topology 8/1, averages any matching rows, and emits one scalar `primary_gap_b`. It does not sweep/calibrate B or produce paired gaps by B. **Minimal fix:** pre-register multiple calibrated B levels (including Poisson), pair both lane runs at each B/topology/repetition, and output the per-B SLO attainments, gaps, and uncertainty.

10. **major — `apps/eval/src/harnext_eval/e6/run.py:445-469, 480-486, 521-525`** — The “Exact scores” block says p50/p99/p99.9 come from HdrHistogram over the burst window. The reported scores use NumPy percentiles over every post-warm-up observation, including pre/post-burst traffic; HdrHistogram is only populated afterward for files. **Minimal fix:** select observations whose intended timestamps fall inside the declared burst interval, compute reported percentiles from the corresponding HdrHistogram objects, and test the values against known histogram fixtures.

11. **major — `apps/eval/src/harnext_eval/e6/run.py:731-750`** — Exact `knee` is the maximum steady rate whose p99 trend is approximately zero and whose lag slope is below threshold. The implementation accepts arbitrarily negative p99 slopes because it tests only `slope <= tolerance`, and if no rate is stable it returns the minimum tested rate as a fictitious knee. The numeric thresholds are defaults rather than recorded pre-registered inputs. **Minimal fix:** apply the pre-registered near-zero criterion (normally `abs(slope) <= tolerance`), require the lag criterion, return no knee/fail when no candidate qualifies, and record thresholds in config/manifest/output.

12. **major — `apps/eval/src/harnext_eval/e6/metrics.py:168-200`; `apps/eval/src/harnext_eval/e6/run.py:961-965`** — Exact `demand(l)` is the minimum `(partitions, workers)` meeting the E6 SLO at each load/cardinality. `demand_curve` groups together both lane designs and every shape, then may select a topology from any of them; it checks `fast_p99` and lag only, not urgent attainment or the batch-fold SLO. The output therefore cannot say which condition the selected demand belongs to. **Minimal fix:** group by lane design, shape/B, load, and cardinality; require all pre-registered D10 conditions; then select the minimal resource tuple within that group.

13. **major — `apps/eval/src/harnext_eval/e6/run.py:503-518, 895-903`; `apps/eval/src/harnext_eval/e6/metrics.py:89-127`** — Exact drain time starts at burst end and returns to the observed baseline lag. The runner passes the end of the entire schedule as `burst_end_s` and hard-codes baseline lag to zero, although the burst ends in the middle of the schedule. “Worker kill” merely delays one coroutine for the default 50 ms and does not kill/restart a worker, so recovery does not measure the specified failure. **Minimal fix:** carry actual burst start/end and measured pre-burst baseline into scoring, and perform/log a real worker kill and restart (or a faithful configured outage) before computing recovery to pre-kill lag.

14. **major — `apps/eval/src/harnext_eval/e6/run.py:337-345, 388-399, 436-453, 480-502`** — The spec requires batch fold latency `window close → commit` and staleness `event → commit`. The fake runner substitutes coroutine completion for a store commit, reports no event-to-commit staleness, and on final flush declares the current flush time to be window close rather than the window's gap/max-age deadline, artificially shrinking fold latency. **Minimal fix:** observe actual fold commit timestamps, retain each window's intended close deadline, and output both close-to-commit and per-event intended-send-to-commit distributions.

15. **major — `apps/eval/src/harnext_eval/e6/run.py:497-501, 535-653`** — Throughput must be measured producer→Kafka and the run must capture per-partition lag, DLQ, duplicates, and misses. The in-process “throughput” is completed observations divided by final simulator time and hard-codes DLQ to zero. The Kafka branch reports neither throughput nor broker lag/DLQ/batch metrics and ignores `cfg`, `lane_design`, and guard overrides, so selecting it cannot execute the experiment and would leave keys required by `run_benchmark` absent. **Minimal fix:** integrate the real pipeline boundaries and telemetry into one runnable Kafka matrix, preserving arm settings and emitting the complete metric schema.

16. **major — `apps/eval/src/harnext_eval/e6/run.py:477-493, 607-650`** — Exact duplicates and missed are required per lane. The in-process path sums away the per-lane counts and, because it appends exactly one observed ID for every queued expected ID with no retry/failure path, always produces tautological zeros. The Kafka loop counts messages rather than unique event IDs, so duplicate outputs can end the loop early and mask a missed ID; it also emits only total misses and no duplicates. **Minimal fix:** preserve per-lane expected/unique observed counters, detect duplicates by ID, wait for all unique IDs or timeout, and write per-lane counts from the external system.

17. **major — `apps/eval/src/harnext_eval/e6/run.py:331-345, 480-496, 1048-1051`** — The validity list requires fake-harness service time to be constant and logged. Actual elapsed service time is an unmeasured `asyncio.sleep`; the result simply repeats the configured number and hard-codes both `service_time_constant` and its check to 1.0. This cannot detect scheduling jitter or a non-constant harness. **Minimal fix:** timestamp every fake-harness start/end, report the service-time distribution, and derive a pre-registered constancy check from those observations.

18. **major — `apps/eval/src/harnext_eval/e6/run.py:688-721, 849-855`; `apps/eval/tests/test_e6/test_runner.py:51-56`** — Calibration must yield p50 about 10 ms and a flat p99. The implementation and test check only p50; the run continues and publishes results when calibration fails, and no p99 trend/flatness is calculated. **Minimal fix:** calculate and threshold both p50 and p99 trend, fail or invalidate the benchmark on failure, and test a deliberately broken calibration path.

19. **major — `apps/eval/src/harnext_eval/e6/run.py:1039-1075`** — The spec's validity list requires broker CPU/disk monitoring. No such samples, output fields, or validity check exist. **Minimal fix:** collect timestamped broker CPU, disk utilization/IO, and saturation alongside every Kafka run and include an explicit pass/diagnostic result.

20. **major — `apps/eval/src/harnext_eval/e6/run.py:881-947, 1020-1093`** — Section 8 requires paired differences with entity-clustered BCa 95% CIs (10,000 resamples) on identical streams. The primary is a difference of unpaired arm means, with no per-entity paired table, CI, or bootstrap; burst cells have only one run. **Minimal fix:** retain per-event/entity paired outcomes from identical schedules, run the specified clustered bootstrap over the lane difference (and appropriate repetition summary for systems metrics), and report CIs beside every contrast.

21. **major — `apps/eval/src/harnext_eval/e6/loadgen.py:278-296, 488-525`** — Urgent gold is derived from the workload artifact itself: events made part of the hot-entity type shift are declared urgent, plus an arbitrary 5% of cold events. This is neither Corpus S's constructed scripted situations nor independent injected urgent events with onset/cost weight. It also makes the primary label definition change with the tested shape. **Minimal fix:** inject a frozen, deterministic situation catalogue independently of load shape, with onset/entity/cost metadata and the same situations replayed in every paired arm.

22. **major — `apps/eval/src/harnext_eval/e6/loadgen.py:433-485, 530-565`; `apps/eval/src/harnext_eval/e6/run.py:896-906`** — Procedure step 1 requires calibrating ON/OFF until realized B matches the fitted target and recording the parameters. `generate_schedule` discards `CalibrationResult` (tail index, convergence, target), `run_benchmark` clamps a negative fitted B to zero, and no failed convergence invalidates a cell. **Minimal fix:** retain and write target/realized B, tail index, iterations, and convergence per run; use the fitted target literally and reject non-converged schedules.

23. **major — `apps/eval/src/harnext_eval/e6/run.py:795-801, 937-959, 1118-1146`** — The named outputs are `latency_hdr/*.hgrm`, `burst_slo.png`, `self_amplification.png`, `demand_curve.png`, and `guards.csv`. Histograms go to `hdr/`, most burst cells have no histogram at all (only anomalous/worker-kill, 1.5×, topology 8/1), and the chart hook writes `e6_burst_slo.png` under a separate `charts/` directory rather than `burst_slo.png`. **Minimal fix:** write every scored burst cell's HdrHistogram under `latency_hdr/` and emit the exact named PNG/CSV outputs at the declared E6 output location.

24. **minor — `apps/eval/src/harnext_eval/e6/run.py:997-1018, 1039-1047`** — Workload parameters must be recorded. The output stores per-entity rates/B/M and a few global scalars, but never records the fitted global type mix or the Pareto calibration parameters needed to reproduce generated schedules. **Minimal fix:** write one versioned workload-parameter artifact containing type probabilities, Zipf fit, ON/OFF parameters, duration, rates, and seeds.

25. **major — `apps/eval/tests/test_e6/test_loadgen.py:51-82`** — The parameterized workload test claims coverage of all schedules but checks only timestamp monotonicity and propagation of `intended_send_ts`. It does not test steady rate, 5×/10-minute benign volume with unchanged mix, exactly three hot entities and a type-mix shift, Zipf skew, Poisson B→0, kill-at-peak, same-seed identity, or independent urgent gold. **Minimal fix:** add quantitative hand-built tests for every declared shape invariant and paired determinism.

26. **major — `apps/eval/tests/test_e6/test_runner.py:18-48`** — The knee test accepts either candidate rate (`knee in {30,120}`), so it cannot catch a reversed/incorrect knee formula, the “no stable rate returns minimum” bug, missing burst-window filtering, or the fake topology. **Minimal fix:** feed controlled trend/lag series with one known knee and a no-knee case, and assert the exact result/failure.

27. **major — `apps/eval/tests/test_e6/test_metrics.py:15-36`** — The metric tests cover only a simple SLO fraction, a two-list gap, one demand row, and one Gini value. They do not compare reported p50/p99/p99.9 against HdrHistogram, test exact drain/recovery timestamps, per-lane duplicate/missed accounting, burst-window selection, fairness, or the complete D10 demand predicate. **Minimal fix:** add literal toy cases for every formula in the E6 “Exact scores” block, including empty urgent populations as invalid.

28. **major — `apps/eval/tests/test_e6/test_runner.py:51-84`** — There is no end-to-end test of `run_benchmark`'s declared condition matrix, budget, paired event IDs, guard effects, repetitions, validity failures, exact output names, or Kafka schema. The chart test uses fabricated one-row tables and checks only that three files exist, so it cannot detect missing/wrong experiment artifacts or vacuous identical arms. **Minimal fix:** run a bounded but structurally complete benchmark fixture and assert the full matrix, exact filenames, paired IDs, non-vacuous expected contrasts, and failure behavior for broken validity checks; add a fixture-backed Kafka adapter test.

**Verdict.** E6 is not faithful to the specification and its results are not trustworthy. The current registered path is a sub-second in-process smoke simulation, leaks urgent gold directly to a hard-coded non-R5 router, does not enforce the admission budget, does not model partitions or lane isolation, leaves key controls and guard ablations vacuous, computes several exact scores on the wrong population or with the wrong formula, omits required telemetry/statistics/artifacts, and is protected by tests that mostly establish that code runs. Before any result can be used, the experiment must run the full paired Kafka matrix from a separate generator, use causal budgeted R5 with independent frozen urgent gold, implement the exact HdrHistogram/SLO/knee/demand/drain formulas and all validity gates, collect real broker/lane telemetry, repeat and cluster-pair comparisons, and add claim-level tests that fail on vacuous arms.
