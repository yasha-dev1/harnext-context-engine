# R1 review — E3 store organisation

1. **Blocker — `apps/eval/src/harnext_eval/e3/run.py:293-306`, `apps/eval/src/harnext_eval/e2/arms.py:187-261`, `apps/eval/src/harnext_eval/stores/build_s4.py:20-28`**
   - **Spec:** E3 compares the actual S0 dump, S1 templated store, S2 flat curated store, S3 curated/indexed store, S4 vector index, and S5 hybrid at equal budgets. In particular, S4 is embedding top-k over raw events and S5 is retrieval over curated files.
   - **Code:** Every store is evaluated as E2 arm `A4`. `A4` only walks Markdown `INDEX.md`/`OVERVIEW.md` and entity-named paths. S4 deliberately deletes those files and contains only `_vector`, so it returns empty material/`UNKNOWN`; S5's vector index is ignored, making its read path the same as S3. S0's index links event-ID paths rather than entity paths, so A4 normally reads only the index, not the event bodies. S2 has no root index, so A4 queues every entity's `OVERVIEW.md` before target-entity files and can exhaust the budget on unrelated entities.
   - **Minimal fix:** Add a store-specific, snapshot-aware material builder: event-dump navigation for S0, entity-folder navigation for S1/S2/S3, actual vector top-k for S4, and vector-over-curated-file retrieval for S5. Apply the same provider-token budget after retrieval and test every path.

2. **Blocker — `apps/eval/src/harnext_eval/cli.py:357-381`, `apps/eval/src/harnext_eval/e3/run.py:206-213`, `apps/eval/src/harnext_eval/e3/run.py:256-266`**
   - **Spec:** S3 is built with three Sonnet seeds; accuracy and health are analysed across seeds; a primary delta is valid only when `|delta| > seed_spread` (between-seed SD).
   - **Code:** The CLI builds and evaluates one seed at a time and writes a separate E3 result per seed. `evaluate_e3` therefore sees one S3 store, sets `seed_spread` to `0.0`, and labels every non-zero delta a reliable difference. There is no later cross-seed aggregation of accuracy or health.
   - **Minimal fix:** Build all three S3 stores first, run the identical frozen probes, then aggregate them in one E3 analysis. Compute and write between-seed SD for accuracy and every health metric, and apply the reliability rule only there.

3. **Major — `apps/eval/src/harnext_eval/e3/run.py:74-87`, `apps/eval/src/harnext_eval/stores/base.py:31-40`**
   - **Spec:** Seed identity is part of the preregistered repeated-store condition and must remain stable for paired comparisons.
   - **Code:** `_store_labels` looks for `store.seed`, but `StoreHandle` has no such field. Duplicate stores are labelled by caller order (`seen[layout]`), so changing list order changes seed identity. This also prevents reliable association of provider/model metadata with a seed.
   - **Minimal fix:** Make seed and builder tier explicit immutable store/run metadata and use them in labels, tables, and joins; never infer seed from sequence order.

4. **Major — `apps/eval/configs/s3-curated.yaml:8-15`, `apps/eval/src/harnext_eval/cli.py:357-379`**
   - **Spec:** Three S3 builds use `claude-sonnet-5`, with a separate `claude-opus-5` build at seed 1.
   - **Code:** The only curated config has one builder model for all seeds and the CLI has no Opus-tier run or separate tier label. If an Opus store were manually passed together with the others, `_primary_contrasts` would incorrectly include it in Sonnet seed spread.
   - **Minimal fix:** Add a distinct Opus seed-1 build, record its tier, report it separately, and compute seed spread from the three Sonnet builds only.

5. **Blocker — `apps/eval/src/harnext_eval/e3/run.py:225-255`, `apps/eval/src/harnext_eval/e3/run.py:240-249`**
   - **Spec:** The exact primary is the difference in E2 `macro_acc` (mean of family means), with a paired entity-clustered BCa CI and McNemar analysis.
   - **Code:** The reported `delta` is a macro-family difference, but its CI is calculated from the unweighted mean of per-probe grades after averaging seeds. Those are different estimands whenever family sizes differ (and this implementation generates an extra code-location set that doubles the combined multi-source family). The bootstrap's own `effect` is ignored, so the printed delta can even lie away from the statistic whose CI is printed.
   - **Minimal fix:** In every entity-cluster bootstrap draw, recompute the exact family means and then `macro_acc`; use that distribution for both delta and CI. Keep seed aggregation explicit rather than averaging grades inside each probe implicitly.

7. **Major — `apps/eval/src/harnext_eval/e2/run.py:108-118`**
   - **Spec:** `macro_acc` is the mean over the five fixed probe families.
   - **Code:** `macro_accuracy` averages only families present in the retained outcomes. If a family is wholly excluded by the leakage gate, absent from a fixture, or failed to generate, its weight disappears and the score can increase rather than becoming invalid.
   - **Minimal fix:** Require the preregistered five-family set and expected counts before scoring; mark a cell invalid if any family is absent instead of silently changing the denominator.

8. **Blocker — `apps/eval/src/harnext_eval/e3/run.py:326-358`**
   - **Spec:** Erosion is the OLS slope of a fixed 60-probe accuracy measurement at replay weeks 1, 2, 4, 8, and end; each probe's question and gold must be correct as of its checkpoint.
   - **Code:** The runner takes ordinary E2 probes frozen at later, probe-specific times and changes only `Probe.T` to each checkpoint. It leaves the question, gold, superseded values, and source event IDs unchanged. Early checkpoints are therefore graded against future/wrong gold and may ask historical questions whose stated time is unrelated to the rewritten cutoff.
   - **Minimal fix:** Freeze a dedicated, stratified 60-probe longitudinal panel whose gold is derived independently at every checkpoint, or regenerate/version checkpoint-specific probe records before the run. Never mutate `T` without recomputing all time-dependent fields.

9. **Major — `apps/eval/src/harnext_eval/e3/run.py:326-327`**
   - **Spec:** The erosion subset is a fixed 60-probe yardstick and should preserve the intended family coverage.
   - **Code:** It selects the lexicographically first 60 hashed probe IDs. This is not stratified, is not recorded as a frozen subset/hash, and can omit or heavily skew families/entities.
   - **Minimal fix:** Select a preregistered stratified 60-probe/entity panel, persist its IDs and hash, and validate identical membership for every store, checkpoint, seed, and corpus.

10. **Major — `apps/eval/src/harnext_eval/e3/run.py:91-109`**
    - **Spec:** Checkpoints are actual replay weeks 1, 2, 4, 8, and end, and slope uses their real replay-week positions.
    - **Code:** For a corpus ending before a requested week, every later checkpoint is clamped to the same end timestamp but retains artificial x-values 1/2/4/8; an additional `end` row is then added. Repeated identical snapshots/accuracies at invented weeks distort OLS.
    - **Minimal fix:** Skip scheduled checkpoints after the corpus end, emit end once at its actual fractional week, and reject duplicate checkpoint timestamps.

11. **Blocker — `apps/eval/src/harnext_eval/e2/run.py:66-74`, `apps/eval/src/harnext_eval/e2/run.py:287-298`**
    - **Spec:** The leakage gate must inspect the events actually delivered to the builder before the selected SHA, reject any event after T, test post-T-only question tokens, and log exclusions.
    - **Code:** E2 passes a delivery log already filtered to `event.time <= T`, rather than the store's delivered-event ledger at the SHA, so the first leakage assertion is true by construction. It also fabricates `gold_action_time = T + 1 microsecond` for every probe and sends gate details first to `/dev/null`, then writes a reduced CSV without reasons. It never inspects material/store contents.
    - **Minimal fix:** Resolve the actual snapshot delivery ledger (event IDs plus times) and materialised content, pass the unfiltered corpus to the gate, apply only probe-relevant assertions, and preserve the gate's reasons in the experiment output.

12. **Blocker — `apps/eval/src/harnext_eval/replay/driver.py:177-193`, `apps/eval/src/harnext_eval/stores/base.py:78-95`**
    - **Spec:** `snapshot(T)` must be a commit containing only events at or before T.
    - **Code:** The cumulative Git store can commit a fast event at a later event time and subsequently flush an older batch window. That later commit is labelled with the old window's `T_last_event`, even though it already contains the fast event from the future. `snapshot(T)` selects solely by the label and can return the contaminated commit. Finding 11's gate cannot detect this.
    - **Minimal fix:** Enforce monotone snapshot watermarks based on the maximum event time ever delivered into each commit (not merely the current fold), or materialise independent lane state before a causally ordered merge. Gate every chosen SHA against its full delivered ledger.

13. **Blocker — `apps/eval/src/harnext_eval/probes/gen_code_location.py:23-45`, `apps/eval/src/harnext_eval/probes/gen_code_location.py:56-84`**
    - **Spec:** For E2/E3 multi-source code probes, T is after the qualifying PR merged, so the linked diff is present in snapshot(T).
    - **Code:** The generator deliberately samples T before the merge and derives files from events in `(T, T+14 days]`. Those gold source events are unavailable to every leakage-safe store at T, so these probes are unanswerable and their score measures future prediction, not store organisation.
    - **Minimal fix:** Generate E2/E3 code probes with T after merge and source IDs at or before T. Keep the pre-merge/future-action formulation, if desired, only in the separately specified E4 task.

14. **Blocker — `apps/eval/src/harnext_eval/probes/gold.py:41-85`, `apps/eval/src/harnext_eval/probes/gold.py:91-143`, `apps/eval/src/harnext_eval/corpus/synthetic.py:46-188`**

**Verdict:** E3 is not faithful enough to support a trusted result. The headline S3-vs-S4 contrast does not query S4, the multi-seed reliability rule is defeated by per-seed execution, longitudinal gold and code-location gold violate their cutoffs, the leakage gate cannot prove snapshot safety, and required populations/providers/validity gates are absent or smoke substitutes. Before results can be trusted, the experiment needs condition-specific retrieval, causally safe snapshots and leakage evidence, correct checkpoint/corpus gold, a real three-seed aggregate (plus separate Opus tier), literal macro/BCa scoring, provider-token budget enforcement, independent health denominators, complete cost/input checks, and non-vacuous tests on the actual layouts.
