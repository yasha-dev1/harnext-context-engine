# Round 2 review — stores and store health

1. **blocker — `apps/eval/src/harnext_eval/e3/run.py:392-504`**. The spec says `acc(S,B)` is literally E2 `macro_acc`, with the E2 reader starting at `INDEX.md`/`OVERVIEW.md` and opening files within the budget (`docs/evaluation-spec.md:271-291,345-357`). E3 instead implements a second retrieval path: it lists the entire snapshot, scans every `OVERVIEW.md` until the entity is found, then supplies all files in the matching directory. Those discovery reads count as tool calls but their contents do not consume the read budget, and this is not E2 A4's link-following traversal. The integration test at `apps/eval/tests/test_e2e3/test_e2e3.py:641-703` checks table shape and non-zero scores, not equality with E2 outcomes. **Minimal fix:** delete the E3-specific text/vector material construction and call the shared E2 store-read arm for every S0-S5 condition; add a test asserting per-probe E3 outcomes and resource logs equal E2 outcomes for the same store, snapshot, provider, and budget.

2. **blocker — `apps/eval/src/harnext_eval/e3/run.py:484-504`**. The spec requires material to be truncated to the budget and real equal-budget evidence to be within ±10%, using the fixed reader/provider (`docs/evaluation-spec.md:271,296-309,337`). E3 preselects and measures material with the module-level fake `truncate_to_tokens`/`count_tokens`; only the later reader call uses the provider tokenizer. For a real Anthropic run, `original_tokens`, fill eligibility, source IDs, and the selected prefix can therefore be wrong even if the final request is re-truncated. **Minimal fix:** use the shared provider-bound tokenizer/material selector from E2 exactly once, and base fill checks and source IDs on that selection.

3. **blocker — `apps/eval/src/harnext_eval/config.py:67-69`, `apps/eval/src/harnext_eval/providers/factory.py:93-103`, `apps/eval/configs/s3-curated.yaml:13`**. S4/S5 must use a pinned embedding model and the real profile must report its identity and recall@10 (`docs/evaluation-spec.md:178,327-328,364`). Configuration only permits `provider: fake`, the factory rejects every non-fake provider, and the real S3 profile explicitly selects fake embeddings. The manual injection seam tested at `apps/eval/tests/test_stores/test_layouts.py:252-272` proves metadata validation, but not that the CLI/configured experiment can run a non-fake embedding provider. Thus R1 FX-stores #7's “supported-not-run” claim is not genuine as an execution-profile claim. **Minimal fix:** add at least one configured real embedding adapter with required model/revision fields, construct it in the factory, use it in the evidentiary config, and test the CLI path (the network call may remain mocked).

4. **blocker — `apps/eval/src/harnext_eval/e3/run.py:863-883,952-1008,1156-1233`**. The spec requires the same fixed 60-probe panel at weeks 1, 2, 4, 8, and end, and OLS over that 60-probe accuracy (`docs/evaluation-spec.md:336,353,357`). The selected panel comes from probe-period probes and `_rederive_probe` drops every probe whose original `T` is after the checkpoint; accuracy is then computed over the shrinking/empty remainder with `require_all=False`. The smoke run demonstrated empty early checkpoints, yet a slope can be fitted to later points. Checkpoint gold is also recomputed only with `PythonGold`; code gold at `apps/eval/src/harnext_eval/e3/run.py:934-949` omits the spec's “merged within 14 d of T” condition. The test at `apps/eval/tests/test_e2e3/test_e2e3.py:741-768` expressly asserts that early probes are dropped, so it fails without the implementation but enshrines the wrong estimand. **Minimal fix:** freeze 60 probes answerable at week 1, rederive all 60 at every checkpoint using the same independently verified gold rules as E2 (including the 14-day PR rule), reject a run if any checkpoint lacks 60 kept probes, and fit OLS only after that check.

5. **blocker — `apps/eval/src/harnext_eval/stores/templated.py:15-16,91-132`, `apps/eval/tests/test_stores/test_layouts.py:135-162`**. S1 must expose every structured field available in the events, including JIRA state, PR merged/closed state, KIP vote outcome, thread-answer state, and Corpus-S world state; 20 folders must be human-reviewed before comparison (`docs/evaluation-spec.md:126,324,363`). Its fixed field set contains only `status`, `assignee`, `priority`, `components`, `fixVersion`, and `linked_keys`. The test exercises only that small hand-picked JIRA fixture, and no review result is accepted or gated. **Minimal fix:** use source-specific deterministic reducers covering the §4 catalogue and arbitrary constructed world-state fields, then require a recorded 20-folder review artifact for an evidentiary run; add one test per missing source/state family.

6. **blocker — `apps/eval/src/harnext_eval/cli.py:305-325`, `apps/eval/src/harnext_eval/stores/build_s3.py:49-68`, `apps/builder/src/harnext_builder/harness/claude_code.py:75-92`**. The spec requires three S3 seeds, fixed prompt hashes, and deterministic settings for paired comparisons (`docs/evaluation-spec.md:330,335,507,562-564`). The CLI seed changes the store name/metadata but is never passed in `HarnessRequest`; that request has no seed/temperature fields, and the Claude harness sets neither a seed nor temperature 0. The three fake builds are also identical deterministic copies. The test at `apps/eval/tests/test_e2e3/test_e2e3.py:641-688` proves only that three labels are aggregated, not that the seed affects a model call or creates independent builds. R1 FX-e3 #9 is therefore only a labelling fix. **Minimal fix:** pass a supported seed and temperature-0/deterministic setting to the provider (or explicitly document and control the provider's available determinism), record it, and test request capture plus repeat identity; do not call identical fake copies a measured between-seed sample.

7. **major — `apps/eval/src/harnext_eval/stores/build_s0.py:18-20,61-73,90`, `apps/eval/tests/test_stores/test_layouts.py:106-129`**. S0 is specified as one event file per event, isolating “the filesystem alone” (`docs/evaluation-spec.md:323`). The builder preserves and regenerates a linked `INDEX.md`, adding an organization/retrieval aid. The cited R1 test genuinely fails if that index is removed, but it verifies the R1 assignment's exception rather than the controlling experiment spec. **Minimal fix:** remove `INDEX.md` from S0 and update the test to assert that only event files and non-reader-visible provenance exist.

8. **major — `apps/eval/src/harnext_eval/stores/build_s5.py:15-56,64-73`, `apps/eval/tests/test_stores/test_layouts.py:275-287`**. S5 is “S3 + embeddings over the store's files” (`docs/evaluation-spec.md:328`). It indexes each whole durable file, including `_meta` provenance, and then manufactures an additional document for every delivered event ID from lines containing that ID. This duplicates evidence, exposes bookkeeping that a reader should not get, and makes exact source-ID retrieval artificially easy. The test queries each event ID literally and therefore rewards the leakage instead of testing natural questions. **Minimal fix:** define/pin a chunker over reader-visible S3 files only, exclude `_meta`, remove event-citation pseudo-documents, attach source IDs only as metadata derived from the chunk, and test natural probe recall.

9. **major — `apps/eval/src/harnext_eval/stores/vector_index.py:186-225`**. S4 is the pinned-embedding RAG alternative (`docs/evaluation-spec.md:327`). Ranking adds a +2 exact-ID bonus and +1 full-query substring bonus to cosine scores, so it is a hybrid lexical/oracle retriever rather than the specified embedding index. Exact-ID tests at `apps/eval/tests/test_stores/test_layouts.py:213-220,275-283` conceal this distinction. **Minimal fix:** rank only by pinned vector similarity (with a deterministic ID tie-break); if lexical retrieval is desired, register it as a separate condition.

10. **major — `apps/eval/src/harnext_eval/health/store_health.py:87-132,358-360`**. The exact `index_acc` denominator is INDEX entries and the numerator is entries resolving to existing files (`docs/evaluation-spec.md:349,357`). The parser recognizes only Markdown tables, so S0/S3 bullet indexes produce zero entries; zero entries are then reported as perfect 1.0. A table row can also “resolve” solely because an entity key directory exists even when its linked target is missing. Existing tests use only tables (`apps/eval/tests/test_grade/test_store_health.py:12-17,79-88`). **Minimal fix:** parse every supported INDEX entry format, require its actual target to exist, and report zero-entry accuracy as N/A (or fail the health check), with bullet-index, missing-target/existing-entity, and empty-index tests.

11. **major — `apps/eval/src/harnext_eval/health/store_health.py:135-159`**. `dangling` is unresolved file/ID references divided by all references (`docs/evaluation-spec.md:350,357`). The scanner checks only Markdown links, wiki refs, and a narrow entity-key regex; it does not validate event/source IDs or other IDs against the delivered-event catalogue. It can consequently miss the principal references written by the stores, while treating raw event text that happens to look like an entity key as a reference. **Minimal fix:** define the store reference grammar, validate file targets and typed IDs against authoritative snapshot catalogues, and add planted missing-ID plus prose false-positive tests.

12. **major — `apps/eval/src/harnext_eval/health/store_health.py:162-205`, `apps/eval/tests/test_grade/test_store_health.py:51-76`**. The exact duplicate metric covers `facts.md` fact lines with MinHash Jaccard ≥0.8 (`docs/evaluation-spec.md:351,357`). The parser counts any non-heading line, including the identical italic template boilerplate emitted in every facts file, inflating duplicate rates. The planted test only duplicates a line byte-for-byte and never checks a near-but-not-exact pair at either side of 0.8 or excludes boilerplate. **Minimal fix:** parse actual fact records/bullets only (excluding template prose), and add deterministic threshold-boundary and boilerplate fixtures.

13. **major — `apps/eval/src/harnext_eval/health/store_health.py:252-300,341`**. `leak_rate` must use entities with at least one ground-truth supersession as the denominator (`docs/evaluation-spec.md:352,357`). Health derives both the denominator and old values from `_meta/superseded.md` inside the store under evaluation. A store that fails to record supersessions receives a perfect zero leak rate, and a curated store can manipulate its own gold. The planted test at `apps/eval/tests/test_grade/test_store_health.py:27-31,51-76` writes that same in-store sidecar. **Minimal fix:** pass an external replay/world-state supersession catalogue at the checkpoint, compare each affected entity's overview against it, and fail/N/A when gold is absent.

14. **major — `apps/eval/src/harnext_eval/health/store_health.py:319-327,342-356`**. The exact over-cap formula is files over 200 lines divided by files (`docs/evaluation-spec.md:348,357`). The numerator contains only UTF-8-readable files, while the denominator includes every file, so binary vector artifacts dilute the S4/S5 rate. **Minimal fix:** specify and use one identical reader-visible/text-file population for numerator and denominator (or define line count for every included file), and test a store containing binaries.

15. **major — `apps/eval/src/harnext_eval/stores/layouts.py:150-202`, `apps/eval/src/harnext_eval/e3/run.py:199-251,583-606`**. The spec requires builder tokens and dollars per 1,000 events, wall time, files touched per run, and every quality number beside tokens/dollars/latency (`docs/evaluation-spec.md:39,338,346,357,509`). Store usage rows do not record wall time; missing time becomes zero, files are summed rather than retained per run, dollars trust optional transcript totals instead of the frozen price table, and E3 hard-codes reader cost to `0.0` even for paid readers. **Minimal fix:** record per-fold elapsed time and immutable provider usage, recompute dollars from manifest prices, preserve per-run rows plus aggregates, and propagate actual reader dollars beside each curve cell; make missing applicable values invalid rather than zero.

16. **major — `apps/eval/src/harnext_eval/stores/build_s3.py:69-108`, `apps/eval/src/harnext_eval/e3/run.py:1296-1303`**. The validity rule says failed folds are counted and a store over 5% is rebuilt after the cause is fixed with a logged amendment (`docs/evaluation-spec.md:366`). The builder logs one failed usage row, restores, and immediately raises, aborting the build before E3 can calculate or enforce the rate; no fixed-cause rebuild or amendment mechanism exists. **Minimal fix:** have the replay/build driver retain failed-fold records, support a declared fixed-cause rebuild, link the amendment, and reject the final store if the post-fix rule is not satisfied.

17. **major — `apps/eval/src/harnext_eval/cli.py:435-463,519-537`, `apps/eval/src/harnext_eval/manifest.py:52-77`**. The spec requires a committed `eval/PREREG.md` and manifests containing replay/probe/config hashes, models, prompts, prices, seeds, and git SHA (`docs/evaluation-spec.md:40,335,562-564`). No `apps/eval/PREREG.md` exists; the CLI never passes `prereg_ref`, records the reader provider name instead of a model ID, does not hash the builder prompt or `CLAUDE.md`, and the standalone store builder writes no manifest. **Minimal fix:** add the append-only preregistration, require its ref for non-smoke runs, hash both prompts/instructions, record exact provider/model/revision/prices, and write a manifest for standalone builds too.

18. **major — `apps/eval/src/harnext_eval/cli.py:504-518`, `apps/eval/src/harnext_eval/e5/run.py:806-815,1026-1037`**. R2 focus item 2 asks whether E5's store/E2 validity can clear on the default real profile. `pyarrow` is now a declared dependency (`apps/eval/pyproject.toml:15`), and smoke reasons are explicit, but `_claim_profile` requires `prereg_ref`, `g4_passed`, `replay_hash`, and `probe_hash` in `CorpusHandle.meta`; the normal CLI populates only generated corpus/probe metadata plus `smoke`, with no config/CLI inputs for the prereg/G4 evidence. Therefore the default real invocation cannot become claim-eligible even if every E2 cadence check passes. **Minimal fix:** add validated CLI/config inputs for the preregistration and G4 evidence, propagate manifest replay/probe hashes into the handle, and add a default-profile test that clears the invalid reasons when all evidence is supplied.

19. **major — `apps/eval/src/harnext_eval/cli.py:466-568`, `apps/eval/src/harnext_eval/e3/run.py:1264-1290`**. E3's named files are now genuinely written and rendered, satisfying R2 focus item 3 for one run, but the spec's `curve.png` is explicitly per store and **both corpora**, and a claim counts only if it holds on both (`docs/evaluation-spec.md:38,317,368`). One CLI run resolves exactly one corpus and overwrites/isolates one E3 result; there is no paired two-corpus aggregation or gate requiring both. **Minimal fix:** support an E3 invocation that consumes both frozen corpus handles, emits corpus-stratified outputs in the named aggregate directory, and refuses a cross-corpus claim unless both required results pass.

## Round 1 fix verification

- **Genuine and meaningfully covered:** FX-stores #4 and #5; FX-e3 #8 and #12; FX-core #1, #11, and #12; FX-e2 #2. Their cited tests exercise behavior that would fail if the corresponding dispatch, metadata, matrix, ledger, snapshot, gate, or vector-read change were removed.
- **Only partial or contrary to the spec:** FX-stores #3 is a real reset regression test but deliberately preserves the forbidden S0 index (finding 7); FX-stores #7 genuinely pins snapshot metadata but its non-fake configured path does not exist (finding 3); FX-e3 #9 creates the requested labels/matrix but does not apply seeds to model generation (finding 6); FX-e3 #10 genuinely rederives some gold, but its test requires dropping future probes and therefore preserves a non-fixed panel (finding 4). The related “supported-not-run” statements are valid only for scale/paid execution, not for the missing configuration paths identified above.
- **Fake-provider vacuity:** the fake path is not identical across all arms in the smoke run (S0/S1/S3/S4 accuracies differ), and `apps/eval/tests/test_stores/test_layouts.py:290-333` would fail if its planted S1/S3 scores became equal. However, the three fake S3 “seeds” are identical builds, so fake health/seed-spread evidence remains vacuous and must stay non-evidentiary.
- **R2 focus execution:** `make eval-smoke` completed and the targeted store/health/replay/E2-E3 suite passed (45 tests). The smoke report contains E3 results, charts, and the actual S3-S4 vector condition. E3's 60-panel, three-seed, and S4-recall checks are explicitly `not-applicable-in-smoke`; the only literal `false` checks in the full report are three E6 checks, outside this module. Passing tests do not cure the semantic findings above.

## Verdict — FAIL

The experiment is not faithful enough for trusted store-organisation results: E3 does not reuse the E2 retrieval/budget path it claims to measure, the erosion estimand is not a fixed 60-probe panel, S1 omits required structured state, real embeddings and seeded deterministic builds are not configurable, and several health/cost formulas are not the spec's literal formulas. Before results can be trusted, those blockers must be corrected, health must use authoritative external denominators and exact reference/file populations, failures/costs/preregistration must be enforced, and a two-corpus real profile must be executable and gated. **Grade: FAIL.**
