## Run

With `GH_TOKEN` (preferred) or `GITHUB_TOKEN` already exported:

```bash
uv run --package harnext-eval python -m harnext_eval.corpus.github_api \
  --repo apache/kafka \
  --since 2019-01-01 --until 2026-07-01 \
  --raw-dir apps/eval/out/corpus/kafka/raw \
  --output apps/eval/out/corpus/kafka/parsed/github.jsonl
```

Repeat exactly the same command to resume. Add `--parse-only` for an entirely offline
parse; this requires every referenced page and needs no token. Missing or invalid
pages fail explicitly, rather than silently producing an incomplete replay.
`write_replay` writes sorted, deduplicated JSONL and its SHA-256 sidecar. The final
JSON summary reports PRs examined, event counts by type, cached/fetched pages and
unique MEMBER/OWNER actor counts among emitted events.

## Implementation

The urllib-only client uses GitHub GraphQL with six retries, exponential backoff
for network failures/5xx and retryable GraphQL errors, and reset/Retry-After waits
on 403/429. Successful responses with remaining quota below 50 also wait. Partial
GraphQL responses with errors are never treated as completed pages.

Raw response JSON is cached atomically under `raw/github`, with readable prefixes
and hashes of the query and all variables. Cursors, repository and commit-window
variables participate in cache identities. PR discovery uses ascending creation
order, scans metadata for earlier PRs too, stops at creation >= until, and fetches
details when updatedAt >= since. This intentionally includes older PRs updated
AFTER until: their earlier activity must not disappear from the historical replay.
Every emitted timestamp is subsequently restricted to [since, until).

Each PR detail request includes metadata, labels, files, reviews with their review
comments, and issue comments. All connections paginate independently. Initial
reviews and nested review comments use 20 nodes to limit multiplicative GraphQL
cost; initial files/labels/issue comments and continuation pages use 100 nodes.
Files retain additions/deletions in raw cache and all paths on the merged event.
The default branch tip is cached and commit history is pinned to that oid across
restarts; associated PR numbers are a cheap first-10 enrichment per commit.

Normalization delegates to `gharchive.parse_event`, preserving its source, types,
PR subjects, existing data fields and push subject selection. Additions include
actor/author routing identity, is_committer, title/body/head issue and KIP keys,
merged_by, labels on terminal PR events, and top-level commit sha/message/branch.
Bodies are truncated to 4,000 characters after key extraction. Contributor keys
use the existing email helper when email is supplied, otherwise case-folded
`contributor:gh:<login>`; deleted/unknown actors have no invented baseline.
Draft/unsubmitted reviews and their comments are not emitted.

## Expected request counts (planning estimate, not measured)

For approximately 10,000 selected PRs during 2019–2026:

- About 100–250 discovery pages, depending on pre-2019 repository history.
- 10,000 PR detail pages.
- One default-branch page and about 100–150 commit-history pages if the window
  contains 10,000–15,000 trunk commits.
- Extra pages for PRs exceeding 100 files/comments/labels, 20 reviews, or reviews
  exceeding 20 review comments. Each continuation returns up to 100 items.

Baseline: roughly 10,200–10,400 requests plus connection overflows; budget roughly
11,000–15,000 requests until actual discussion/file distributions are known.
Retries add requests; a complete restart/parse uses zero network requests.
GraphQL points are not request counts. Nested review connections can cost multiple
points; actual headers control throttling, so elapsed time is not estimated here.

## Data limits and integration questions

- Text, associations, labels, and refs are API snapshots. Edited/deleted content,
  prior review states and earlier close/reopen cycles cannot be reconstructed
  from these fields. Opened events do not carry later merge state, merge SHA,
  changed files or merger identity, but their title/body/ref still reflect the
  fetched snapshot. Does the preregistration explicitly accept this limitation?
- The PR snapshot supplies mergedBy, but no closing actor or association of the
  merger. Terminal-event actor association remains unknown and is_committer is
  false; original PR association is preserved as `pr_author_association` there.
  This avoids attributing a PR author's MEMBER status to someone who merged it.
  K2 may enrich these actors from its roster. No timeline request is stubbed in.
- Push events represent commits authored on the default branch, not historical
  push operations. The commit author is used as actor; actual pusher/time and
  actor association are unavailable in commit history. Push subjects follow
  GH Archive's issue/KIP/contributor/fallback rule; only PR events use `pr:N`.
- API and GH Archive IDs differ because the API exposes object IDs, not original
  event IDs. Do not combine both extractors for the same window without a separate
  semantic deduplication policy.
- This extractor does not fetch CI/check failure events. K2 must report the trunk
  CI failure/fix labeling function's lack of coverage if no other source adds CI.
- Cache entries are immutable snapshots, including PR discovery update timestamps
  and the default-branch tip. Use a fresh raw directory to refresh the snapshot;
  resuming an existing directory deliberately reuses its observations.
- No live repository fetch was performed. Current GraphQL review/comment field
  conventions were checked against the official GitHub reference:
  https://docs.github.com/en/graphql/reference/pulls
