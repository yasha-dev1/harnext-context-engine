# T2 replay, snapshots, and leakage-gate status

## Built

- `src/harnext_eval/replay/driver.py`
  - deterministic `run_pipeline()` over sorted `EvalEvent` records on the event
    clock;
  - `RouterPolicy` seam plus the config-driven rules-only floor;
  - rules and budgeted deviation routing, optional router guards, and single- or
    two-lane handling;
  - per-`(mgtenant, subject)` batch windows closed by gap, event cap, max age,
    cutoff, or end-of-stream flush;
  - immediate fast folds, batch window folds, `RouterRecord` callbacks, and
    `DriverStats` with every `SnapshotRef` returned by `StoreHandle.fold()`.
- `src/harnext_eval/replay/kafka_replay.py`
  - async JSONL producer for `cms.events.raw.v1` at event-time speed-up or an
    open-loop fixed rate;
  - inclusive cutoff and deterministic `intended_send_ts` stamping;
  - lazy `aiokafka` import and producer protocol for broker-free fake tests.
- `src/harnext_eval/replay/snapshots.py`
  - deterministic last-eligible snapshot lookup, including CSV-order tie-breaks;
  - detached temporary checkout materialisation from a `GitBackend`.
- `src/harnext_eval/replay/gate.py`
  - leakage checks for post-T deliveries, snapshot watermark, question tokens
    found only post-T, gold-action time, and gold-action envelope presence;
  - CSV/JSONL/in-memory delivery logs and append-only `out/gate.csv` audit rows.
- `src/harnext_eval/replay/__init__.py` exports the driver contract.
- `tests/test_replay/` covers the synthetic corpus, gap/cap/max-age closure,
  rules and score routing, cutoff, snapshot lookup/materialisation, Kafka fake
  production, and gate PASS/FAIL cases.

`StoreHandle.fold()` already appends its returned reference to the store's
`snapshots.csv`; the driver deliberately invokes it once per fold and does not
append a duplicate row.

## Stubbed or deferred

- No broker is required for tests. A real replay creates `AIOKafkaProducer`
  lazily only when no producer is injected.
- A deviation scorer is not defined by T2. E1 supplies it through the
  `RouterPolicy` protocol; the default policy remains rules-only as required.

## Integration notes

- T0 does not define a delivery-log record type. The leakage gate therefore
  accepts `EvalEvent` objects or mappings loaded from CSV/JSONL and recognises
  `event_time`/`time`/`t` plus `snapshot_sha`/`commit_sha`/`sha`. A later shared
  delivery-log model can plug into this without changing gate semantics.
- The optional `policy=` keyword on `run_pipeline()` is the E1 integration seam;
  callers using the PLAN.md signature require no changes.
