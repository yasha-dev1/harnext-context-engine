# Merged E2 smoke: verified 2026-09-12

**The initial E2 infrastructure smoke passes.** Thirty live reader probes across
three stores completed with valid typed output inside the configured retrieval
budget. Every logged tool return was reproduced from the exact saved snapshot.
The full scientific configuration matrix is still a later development stage.

## Harness used

Harnext's production builder runner and Git snapshot backend, with the Codex CLI
adapter in **host-controlled file-tool mode**. Builder and reader both use
**`gpt-5.6-luna`, medium reasoning effort**, through authenticated Codex CLI
**0.154.0**. Model substitutions and fake fallbacks are disabled.

The native-shell mode failed at sandbox initialization on this host:
`bwrap: loopback: Failed RTM_NEWADDR`. File-tool mode gives the model no native
shell; Harnext performs allowlisted reads/writes and rejects path escapes and
symlinks. It does not bypass the native sandbox. A future native-shell harness
comparison still needs a working environment.

## Results

Each store answers the same ten questions, two in each family: extraction,
temporal, update, multisource and abstention. The source fixture has six events
and two completed windows. Earlier snapshots are queried after later state exists.

| Store | Valid completion / budget | Exact values | Strict evidence | Snapshot/tool replay |
|---|---:|---:|---:|---|
| S3: Codex-maintained indexed files | 10/10 | 9/10 | 8/10 | PASS |
| S1: deterministic fixed template | 10/10 | 7/10 | 8/10 | PASS |
| S0: raw event files | 10/10 | 9/10 | 9/10 | PASS |

The strict evidence score is separate from answer correctness. It checks required
source IDs and actual exposure, not general semantic entailment. An abstention
with irrelevant citations can receive value credit and fail the evidence rule.
The separate exact `source#ID` diagnostic changes none of these final scores.

These figures establish useful measurement behavior; they do **not** establish
that S3 is better than the controls. There is one tiny constructed workload,
one built store per condition, and no uncertainty estimate or held-out evaluation.

## What the failures tell us

- **S1 drops arbitrary fields.** Its fixed projection does not preserve the
  release-freeze date, so both date questions become unanswerable from that store.
  The planned lossless/ledger deterministic baseline is necessary before testing
  whether model curation beats a strong cheap alternative.
- **The complete cross-source file set is missed in all three arms.** S3 returns
  only `tests/test_cache.py`; S1 and S0 abstain. These failures occur with five
  retrieval actions plus the reserved final answer. Keep them in the results;
  test tool policy and read/call budgets on development data.
- **S3's current issue projection drops the older PR link during the update.**
  PR-71 still exists in its own entity and the history, but the updated issue
  overview/facts mention only PR-72. The failed file query follows the newer link.
  This exposes a preservation/navigation interaction for the template and writer
  policy experiments; it does not by itself isolate a single causal factor.
- **One S3 abstention cites the freeze-date event.** The actual production release
  timestamp is absent, so abstaining is correct, but the strict unknown-evidence
  rule rejects the citation. Freeze the abstention/evidence contract before the
  real pilot so presentation policy cannot confound an engine comparison.

## Engineering fixes verified during the smoke

Incomplete builds, adapter errors and no-edit Codex completions now fail and roll
back instead of publishing a snapshot. The reader's last completion is reserved
for a typed answer or unknown, preventing endless searching from consuming the
entire call allowance. The prompt explicitly requests raw event IDs. A stale
configuration-identity cache can no longer misstate offline mode.

The final retests reused the original six snapshot SHAs and made **zero additional
builder calls**. The three arms ran concurrently to reduce wall time; their
latencies are not a serial performance benchmark. Earlier diagnostic attempts
remain on disk with failed/interrupted status and are not counted as successful
quality trials.

## Validation and accounting

` .venv/bin/pytest apps/eval/tests apps/builder/tests -q `: **363 passed**, with
10 existing numerical/multiprocessing warnings. The merged-E2 tests also pass
after the final reader/reuse changes. Changed files pass Ruff; the new modules
and adapters pass Pyright using the workspace interpreter. Two unrelated,
pre-existing E1 lint findings remain documented in the integration status.

Successful source S3 builds consumed 117,604 reported input tokens and 5,390
output tokens. Final reader retests consumed 1,073,382 input tokens and 12,702
output tokens. Cached input is included within input totals. These counts exclude
exploratory/interrupted attempts, and the retests did not repeat the builder work.
USD billing is unknown. Retrieval is capped at **32,768 UTF-8 bytes**, independently
of provider token usage; this is not an exact 8k-token experiment.

## Next stage

1. Freeze exact tokenizer/cost accounting and the typed citation/abstention contract.
2. Add the strong lossless deterministic baseline and a small real-data development

template/retrieval/graph matrix, pinned token-budget comparisons and confirmation
statistics are **not yet implemented in this merged path**. The engine is ready
