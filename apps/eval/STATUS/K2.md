
Fresh generation: **6.57 s, 598,012 KiB peak RSS**, exit 0. The final E1
measurement uses the fresh canonical `out/k2-scale/generated.jsonl`, SHA-256
`26ded231f156f4ed760f70eaed8aa301430c0e0aefc43d415d38bcc0c7d7fa02`.
An exhaustive JSON comparison also verified that the recovered replay had
identical event payloads. Hardware: AMD Ryzen 7 3800X, 8 physical cores / 16
logical CPUs, 31.2 GiB RAM, Linux; four policy workers and one BLAS thread each.

Earlier profiling attempts were stopped to remove repeated monthly feature
folds and full-stream VUS scans in the 200-repeat random sanity check. VUS now
visits only buffer boundary slices and uses sorted cumulative credits for each
inclusive threshold. Tests compare against the former dense formulas on
irregular/duplicate timestamps and tied scores at absolute tolerance 1e-12;
the reference toy-metric tests also pass. No thresholds, repetitions, budgets,
policies or metrics were removed to improve the performance result.

Final full E1 measurement (exit 0, all 8 policies × 4 budgets, 52 evaluation
months, metrics/robustness/calibration/200-repeat sanity checks, Parquet and
results JSON included):

| Measurement | Result |
|---|---:|
| E1 wall time | **1,938.74 s = 32 min 18.74 s** |
| Parent peak RSS | **4,274,148 KiB = 4.08 GiB** |
| Largest worker peak RSS | **3,297,344 KiB = 3.14 GiB** |
| Peak summed proportional set size (PSS) | **6,128,990 KiB = 5.85 GiB** |
| Compact score rows | **3,109,760** (97,180 evaluated events × 32 conditions) |
| Parquet row groups | **32**, at most 100,000 rows each |
| Parquet size | **104,720,389 bytes (99.87 MiB)** |

The approximately 8 GiB limit is met on this completed 100k run. RSS is from
`resource.getrusage`; summed PSS was sampled once per second from the process
tree's `/proc/*/smaps_rollup`. Summing raw RSS across forked workers counts
shared pages repeatedly (the observed sum reached 15,940,984 KiB); PSS gives
the shared-memory-adjusted footprint. Sampling can miss brief peaks; the
per-process RSS high-water marks do not depend on that sampling interval.

Exact measurement command, run from the repository root:

```sh

uv run python -m harnext_eval.e1.benchmark \
  --replay apps/eval/out/k2-scale/generated.jsonl \

```

A streaming audit verified every score column against the preceding full run,
all 3,109,760 rows, strictly ordered unique event IDs per policy/budget, all
32 conditions with 97,180 events each, correct population flags, JSON-string
features, ZSTD and bounded row groups. Audit evidence is saved in
`out/k2-scale-final/artifact-verification.json`.

Raw measurements: `out/k2-scale-final/performance.json`; artifacts:
`out/k2-scale-final/e1/`. Background applications were active; load average
was observed near 21 on this 16-logical-CPU host. The final run therefore
also measures host contention. Splitting R5 budget jobs is tested equivalent
but did not yield a demonstrated speedup in these non-isolated measurements.

**350k extrapolation:** simple 3.5× scaling gives **6,785.59 s ≈ 113.1 min
(1 h 53 min)** on the measured configuration. This is an estimate below the
2-hour target, not a measured 350k result or a certified 20-core timing.
Conservative linear memory planning gives **14.27 GiB parent RSS / 20.46 GiB
summed PSS**. The 8 GiB result is established for 100k only; it must not be
advertised for 350k. Actual memory scaling is affected by the fixed row-group
size, trailing fit cap, entity distribution and event payload sizes. The real
corpus also requires weak-label construction, which constructed-label timing
does not measure. A complete 350k real replay should be profiled before
claiming its final runtime or memory bound.

Features are folded once in time order over the selected window, including
tuning months; rolling numeric baselines retain four weeks. Model fitting and
threshold calibration use only the trailing 12 calendar months, strictly
before the evaluation month. The feature cache retains those months plus the
current month. Actor/subject novelty follows prior observations in the window.
Four forked workers score policies and independent R5 budgets on Linux; `HARNEXT_E1_WORKERS=1` forces the
serial fallback, also used below 5,000 events or when fork is unavailable.
BLAS thread limits avoid oversubscription. Tests compare serial/forked R3/R5
scores exactly. Compact Parquet uses one row per event × policy × budget,
`rule_negative` as a boolean, features as JSON strings, and PyArrow ZSTD in
100,000-row groups. Serialization never constructs a second full-table JSON
string/Arrow copy. The preceding whole-table-write run took 1,716.45 seconds
and peaked at 8,483,140 KiB RSS (8.09 GiB), motivating this bounded writer.
Small in-memory callers retain the historical population view; results JSON
never expands the score table.
