# Arm `F5` — Harnext as shipped (the product's batch lane)

Decision of the thesis author (2026-09-20): F5 is the product on the **write side** too — the
builder's batch lane — not the eval's Zhou-style A.1 agent with an "F5 layout" block. The former
F5 (prompt `GRANULARITY["F5"]`, `F5_SCHEMA`/`F5_INDEX` seed, 200-line-cap reporting) is retired;
no arm uses it. Implementation: `stores/product.py` (everything product-specific) and class `F5`
in `stores/llm_files.py`. Shared store mechanics: [README.md](README.md).

Everything in the left column is **imported from the product package, not copied**, so a change
in the product changes the arm (and its digest, `product.digest()`, recorded as
`prompts_sha256` in `build-state.json` — F5 has its own digest, separate from the other arms').

## Read access

- Like every F arm: Harnext's production interface, the MCP tool `context_research(question)`
  (`arms.yaml` `mcp_kind: research`; `mcp_server.py` `ResearchBackend` → `harnext_mcp/research.py:
  research_dir`, Claude Code harness on `claude-haiku-4-5-20251001`, 40 turns / 180 s per
  question, 25 questions per trial). **F5 is the Harnext system arm on both sides**: the store
  the product's builder writes, read by the product's research agent.
- Recorded deviation (all F arms): the product prompt's *"Start from INDEX.md to navigate, then
  read the relevant entity files"* becomes *"Start from INDEX.md if present, otherwise from the
  top-level listing, then read the relevant files"* — for F5 this removes a hint the product
  itself would give; the effect (if any) is against F5, not for it.

## What an examiner should know

- F5 no longer shares a builder prompt with F4/F6. F5 − F4-entity is therefore "product builder +
  product layout" vs "Zhou A.1 builder + one-file-per-entity", not an isolated layout effect;
  the builder *model* and the reader are the same.
- The product prompt does not describe the reader, does not mention `_unprocessed/`, and asks
  for minimal edits; none of that was "improved" for the benchmark.
- `CLAUDE.md` sits in the store and is visible to the reader like any other file (as in the
  product).
- The retired F5 strings remain in `stores/prompts.py`, marked frozen, only because the shared
  `prompts.digest()` is pinned in the manifests of the F2/F3/F4-*/F6 builds in progress; they
  are unreachable from arm F5 and go when those stores are rebuilt.
- Live check (2026-09-20, Haiku 4.5, first 60 smoke-stream events, 2 slices of 30, all inline):
  0 failed windows; $0.30 / 112 s / 17 turns and $0.24 / 96 s / 39 turns; 11 entities, each with
  `OVERVIEW.md`, `facts.md`, `timeline.md`, and an `INDEX.md` row. The builder filed PRs as
  `entities/pr/apache__kafka/<n>/` (repository as a folder) in both slices, not the
  `apache__kafka__<n>` the seed's slug rule literally gives; this is the builder's reading of
  the product manual and is not corrected by the eval.
- Offline: `--builder fake` writes the product layout deterministically
  (`product.FakeProductBuilder`), reading the events from the instruction (or the mount).
- Full build: `ARMS=F5 apps/eval/out/kafka-500-v2/runs/start-store-llm.sh` (under systemd) =
  `python -m harnext_eval.e2.v2.stores.build --arm F5 --scope full --builder claude
  --window-events 250 --window-bytes 400000`.
