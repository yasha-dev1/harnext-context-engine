# Arm `F2` — foldered: LLM designs a taxonomy, F0 files moved intact

Source: Zhou et al. §3: *"Foldered sessions has an LLM design a folder taxonomy into which the
Verbatim dump's session files are moved intact (move only, zero byte edits), so the taxonomy is the
only signal added over the Verbatim dump."* App. C.4: *"the Foldered sessions pass runs view, grep,
and rename alone."* Plan row F2: *"F0's files moved into an agent-designed folder taxonomy; no
content edits; weekly reorganisation pass."* Implementation: class `F2` in `stores/llm_files.py`,
move-plan surface, prompts and digest in `stores/foldered.py`. Shared decisions: [README.md](README.md).

| paper says | what the code does | deviation (and why) |
|---|---|---|
| Move only, zero byte edits. | `prepare()` writes the window's F0 files. The builder never moves a file itself: it writes a **move plan** `_moves.json` (`{"from": "to"}`, continued in `_moves-2.json` … for long plans; a target ending in `/` keeps the file name). `F2.verify` first requires the tree to be byte-identical to before apart from the plan files, then `foldered.execute` validates the whole plan (every source exists; every target is a new, normalized `.md` path inside the tree, not under `.git`/`_event`/`_unprocessed`; no target named twice, none existing, none colliding with a file/folder) and only then performs `os.rename`s and deletes the plan. **Verified after every window**: the multiset of file sha256s before and after must be equal (`verify_moves`); at build end the file count must equal the event count (`audit`). | **Recorded deviation: a plan file instead of a rename tool.** The paper's agent calls `rename`; ours declares the renames and code performs them. Reason: the Claude Code harness has no rename tool and its sandboxed Bash cannot start on the build host (`bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted` — every `mkdir`/`mv` of the first build failed, all windows ended "no change to the store"). The plan is arguably closer to "move only": the agent has no means to edit, copy or delete. A violating window is discarded and retried, then falls back to leaving the files at their F0 paths. |
| Tools: view, grep, rename. | Permission rules `Read(./**)` (covers Read, Glob, Grep — inside the store only) and `Edit(./_moves*.json)` (Write, only to the plan files) under the harness's default-deny mode; Bash, web and sub-agent tools denied. Checked live: writes to `notes.md`, `../x`, `/tmp/x` and reads/greps of `/etc` are refused by the harness. | No shell at all; rename = plan entry; `mkdir -p` is implicit (as in the paper's rename). |
| The taxonomy is the only added signal. | The builder may also **rename files** ("give a moved file a name that tells a reader what it is (keep the `.md` extension and keep the event's identifier in the name)", `foldered.ROLE`). | **File names are a second signal** beyond the folder tree. Kept because a folder of 400 files named `jira-12345-change-7.md` is not navigable; the id-in-name rule keeps grep-by-id working. The paper's session files were already named by session. |
| One pass over the finished dump (C.4: a "pass"). Plan: weekly reorganisation. | Incremental: every window (25 events / 60 kB) the builder moves the new files out of `events/` and *"may also re-home earlier files"* (`foldered.ROLE`, `foldered.INSTRUCTION`). | Cadence is per window, not weekly/one-shot: the taxonomy grows with the stream like the curated arms, which makes F2 comparable to them at every checkpoint. |
| System prompt: taxonomy contract. | `foldered.system()` = ROLE (role, how to move, paths) + READER + TAXONOMY + NAMING + OUTPUT: the five properties verbatim (`22-28`) and the naming guidance (`53-57`). **Not** included: SHAPE example, STRATEGY, PRINCIPLES (frontmatter/cross-refs/locators are meaningless when bytes cannot change). | The paper does not print the foldering prompt; this one is assembled from its A.1 blocks. |
| — | Failed window fallback: files stay at `events/YYYY/MM/DD/` — i.e. F0 layout inside F2; no `_unprocessed/`. | Nothing is lost; unmoved files are visible as "not yet filed". |

## What an examiner should know

- **Byte identity is machine-verified** for every window and at build end; a store that passed
  `audit` has exactly one file per event with F0 content. Quote `verify_moves` and the count check.
- The builder sees the listing of new files (path, type, entities, title) and a code-computed
  listing of the current folders with file counts (`foldered.folders`), not the bodies, unless it
  opens them.
- Two signals differ from the paper: file renames and incremental cadence. Both are documented in
  F2's own prompt hash (`foldered.digest()`, pinned in the store manifest; the retired
  `FOLDER_ROLE`/`FOLDER_INSTRUCTION` in `prompts.py` stay frozen because the other arms' pinned
  `prompts.digest()` covers them).
- F2 − F0 isolates "does an LLM-designed tree help a grep/ls reader", the plan's stated purpose
  (blueprint §159: *"its test at matched checkpoints isolates taxonomy"*).
- Cost is the lowest of the LLM arms (no writing); still one Haiku 4.5 run per window.
